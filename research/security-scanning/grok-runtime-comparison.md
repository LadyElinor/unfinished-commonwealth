## One proposal, three boundaries

Suppose a tool is asked to sample site A and its proposed arguments change to site B before dispatch. The systems have different units of approval and different observable effects.

| Question | Grok Build CLI | CORTAC scratch gateway | Unfinished Commonwealth |
|---|---|---|---|
| What does the reviewer see? | The inspected pre-tool path validates rewritten arguments and rebuilds the envelope. An upstream test checks the rewritten destination in the permission prompt. | A proposal binds the case, policy epoch, expected revision, target, value, evidence and consequential decision record. Receipts and the mandate refer to the precise proposal. | The research gate compares actor, team, action and effective JSON argument digest with the fixture grant. The participant transport is a separate proposal-submission mechanism. |
| What happens on approval? | A prepared call proceeds through applicable permission handling to a configured tool. ACP is the client protocol. The actual effect depends on the selected tool and sandbox configuration. | Commit rechecks receipts, participants, grant, revocation, expiry and prior use under the same local transaction that writes the scratch effect and journal. | A successful research-gate check returns a Boolean and appends an in-memory audit entry. The distinct participant host owns the proposal database and issues the transport receipt. |
| What can be verified afterward? | The source and tests identify the expected prompt contents. A permission response alone supplies no observation that a particular effect occurred. | The auditor checks the current stored effect and revision. The checker reconciles fixture inputs, receipt and effect digests, state and journal order. | The lightweight gate records the argument digest for a parameterized check. The isolation harness compares host accounting and receipt identity on retried submissions. |
| Who controls the checker? | A project agent definition can take precedence over a user definition of the same name. Trust in project configuration and the identity of a reviewer require separate treatment. | Reviewer/controller exclusions operate on constructor-supplied identities. The Python harness controls the fixtures, gateway and checker. | The Linux isolation experiment separates a host and participants by OS identity. Its trusted supervisor and host remain inside the experiment's trust assumptions. |

## Observed local results

- In the Commonwealth research gate, a fresh grant for site A produced **allow A, deny B, allow A again, revoke, deny A**. The repeated allow was a second decision with zero tool executions. The grant remains usable until revoked in this fixture. [Gate implementation](https://github.com/LadyElinor/unfinished-commonwealth/blob/23b681e6557eacb3b1cfa576ac77c84a1c3ad368/research/security_scanning/authorization.py)
- CORTAC's checker passed all 42 synthetic episodes. In the Space ROS profile the changed proposal with the original receipts was refused with zero effects. Fresh review receipts for the changed proposal still left zero effects under the original mandate. Repeating the original audited request left precisely one effect and a recorded rejection for a stale revision. Code inspection separately confirms that a successful commit consumes its mandate. [Commit and audit](https://github.com/LadyElinor/CORTAC/blob/75fd8f979502eb9f81ce380577939c9c3ec33dc7/package/wac_offline/runner.py#L346)

Its recount of the preserved CORTAC export found nine audited effects, 33 episodes with no effect and three rolled-back command-sink failures. Both checks use the same CORTAC fixture lineage. ## Integration decision

Use a Build/ACP client as a **proposal producer**. Give a separately administered host sole control of policy, grants and the effect adapter. Let it resolve the target and evidence, canonicalize the final arguments under its own versioned contract, and present those arguments for review. Bind the tool identity, proposal revision, evidence digest, scope, expiry and use limit at the host. The executor rechecks them at commit. A client-side hook can explain early refusals and show revised arguments to the operator.

The next discriminating test uses a new argument-bearing proposal and an independently controlled effect sink in an owned disposable setup. Record one approved effect at A, zero effects for B under the A grant, zero extra effects on retry, and a journaled failure with unchanged state if the sink fails. Have a second controller read the sink and compare it with the journal. Keep an ambiguous external outcome open for reconciliation. A local SQLite rollback does not establish rollback across a remote API.

This is a proposed integration. The present evidence covers a source-level inspection and two offline replays. The upstream Rust tests, live hosted controls, actual reviewer independence and end-to-end integration across the three systems remain unverified.
